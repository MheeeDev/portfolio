## Problem

A dairy plant's production rooms are warm and wet from washing and steam. Without moving air,
condensation forms on the ceiling and drips back down — a hygiene problem. The plant added a
ventilation system: one blower on a VFD feeding a duct header with **11 motorised air valves (F1–F11)**.

The ventilation had to follow what production was doing — running, cleaning in place (CIP) or needing
full airflow — and that knowledge lived in an **S7-300** and an **S7-400** already running the lines.
Hardwiring status between panels in a hygienic area is slow and leaves no room to grow.

## My role & scope

I was the project engineer and wrote everything new:

- **S7-1200 program** — blower speed and start/stop, valve positions, NORMAL and FULL modes, off-delays, alarms
- **PUT/GET link** — the S7-1200, through its CP 1243-1, reads from and writes to both production CPUs
- **HMI** — seven screens designed in-house on a TP700 Comfort
- **Site work** — testing with both production CPUs running, and balancing airflow at each valve

## Approach

### The new controller asks, the old ones only answer

With PUT/GET the **client** does all the work. The S7-1200 runs GET and PUT; the S7-300 and S7-400
answer from their operating systems. On their side the plant only needed a data block and a few
networks that write a heartbeat and status into it — the running production programs were barely touched.

### Two networks, one gateway

The plant network with the S7-300 and S7-400 comes in on the **CP 1243-1**. The S7-1200's own port
and the HMI sit on a separate machine network behind a SCALANCE XB005. The plant side cannot see the HMI,
and only the agreed data block crosses — which matters, because PUT/GET has no authentication.

### One layout, one owner per byte

Each partner has a 20-byte `DB100` at fixed offsets, mirrored in a standard-access DB on the S7-1200.
Bytes 0–7 are written by the partner (heartbeat, run / CIP / request-full bits, demand). Bytes 8–19 are
written by the S7-1200 (heartbeat, blower running and Hz, valve bits F1–F11, alarm word). No byte has
two writers, so values never fight.

### One job at a time, and trust the heartbeat

Four jobs run in turn: GET S7-300, PUT S7-300, GET S7-400, PUT S7-400. Each job's `REQ` is true only on
its turn, which gives a clean rising edge each round with no clock pulses. A finished GET is not proof of
life — a CPU in STOP still answers with stale data — so each partner's heartbeat must change within three
reads, or the zone holds NORMAL airflow and an alarm is raised. The last `STATUS` of every job is shown on
the HMI's network page.

### Air balanced on site

The ducts to F1–F11 differ in length and bends, so the valves near the blower would take most of the air
if all opened fully. Openings were set valve by valve from air-velocity readings on site — 100 % at F1
down to 45 % at F4 — and kept on the HMI's parameter page. On stop, the blower runs on for 30 s and the
valves close after 60 s, so the blower never pushes against closed valves.

## Delivery

- S7-1200 program and PUT/GET link in TIA Portal, with standard-access interface DBs
- Seven HMI screens: Home, Overview (room layout with duct and valves), Manual, Auto (NORMAL / FULL),
  Alarm, Parameter and Network
- Site testing with both production CPUs running, and valve-by-valve air balancing

## Result

- Ventilation follows production state from two older CPUs with no added hardwired signals
- New signals fit into the spare bytes of the shared layout without moving any offset
- A lost partner or a stopped CPU shows as an alarm with a status code, not as quiet wrong behaviour
