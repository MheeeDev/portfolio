ห้องผลิตในโรงงานนมมีทั้ง **ถังสแตนเลส ไอน้ำจากการล้าง และความชื้น** ตลอดวันครับ
ถ้าอากาศไม่ไหลเวียน ไอน้ำจะเกาะเพดาน หยดลงพื้น และกลายเป็นปัญหาความสะอาด
งานนี้คือ **ระบบระบายอากาศ** ที่มี **Blower** หนึ่งตัวขับด้วย Inverter ส่งลมผ่านท่อไปยัง **วาล์วลม 11 จุด (F1–F11)** ในห้องต่างๆ

เพื่อให้ลมเปิดตามสิ่งที่ไลน์ผลิตกำลังทำ เราเลือกใช้ **PUT/GET** ครับ

สองเครือข่ายนี้ไม่ปนกัน ใครอยู่ฝั่งโรงงานมองไม่เห็นหน้าจอของเรา และ HMI ของเราก็ไม่ต้องรู้จัก PLC ของไลน์ผลิตเลย

## PUT/GET คืออะไร แบบเห็นภาพ

ลองนึกว่า S7-300 มี **กระดานไวท์บอร์ด** (Data block) แขวนไว้หน้าห้อง โดยตัวมันเองไม่ต้องทำอะไรเพิ่ม

- **GET** คือ S7-1200 เดินไป **อ่าน** กระดานของ S7-300 แล้วจดกลับมาใส่สมุดของตัวเอง
- **PUT** คือ S7-1200 เดินไป **เขียน** ลงบนกระดานของ S7-300 ในช่องที่ตกลงกันไว้

ฝั่งที่เดินไปหาเรียกว่า **Client** (ในงานนี้คือ S7-1200) ฝั่งที่ถูกอ่านถูกเขียนคือ **Server** (S7-300 และ S7-400)
ข้อดีที่ทำให้เราเลือก PUT/GET คือ **ฝั่ง Server ไม่ต้องเขียนคำสั่งสื่อสารเลย** ระบบปฏิบัติการของ CPU ตอบให้เอง
สิ่งที่ต้องทำฝั่ง S7-300 / S7-400 มีแค่ **เตรียม DB** และ Network สั้นๆ ที่เขียน Heartbeat กับสถานะลงไป และอ่านค่าที่ S7-1200 PUT มาไปใช้
โปรแกรมไลน์ผลิตที่เดินอยู่แทบไม่ต้องแตะ ซึ่งสำคัญมากในโรงงานอาหารที่หยุดไลน์ได้ยาก

| | GET | PUT |
|---|---|---|
| ทิศทางข้อมูล | Partner → S7-1200 | S7-1200 → Partner |
| พารามิเตอร์ฝั่งเรา | `RD_1` ที่เก็บค่าที่อ่านมา | `SD_1` ค่าที่จะส่งไป |
| พารามิเตอร์ฝั่ง Partner | `ADDR_1` ชี้ไปที่ DB ของ Partner | `ADDR_1` ชี้ไปที่ DB ของ Partner |
| บอกว่าเสร็จ | `NDR` = 1 หนึ่งรอบ | `DONE` = 1 หนึ่งรอบ |
| บอกว่าพัง | `ERROR` = 1 พร้อม `STATUS` | `ERROR` = 1 พร้อม `STATUS` |
| เริ่มงานเมื่อ | `REQ` ขอบขาขึ้น | `REQ` ขอบขาขึ้น |

## ออกแบบ Data block ให้ตรงกันทั้งสองฝั่ง

S7-300 และ S7-400 อ้างถึงข้อมูลด้วย **Address แบบตายตัว** (DB100.DBW0, DB100.DBX2.0 ...) เราจึงวาง DB ให้ **ทุกไบต์อยู่ตำแหน่งเดียวกันทั้งสองฝั่ง**
และแบ่ง DB เป็นสองโซนที่มี **เจ้าของคนเดียว**: ไบต์ 0–7 Partner เป็นคนเขียน ไบต์ 8–19 S7-1200 เป็นคนเขียน
จะไม่มีวันที่สองเครื่องเขียนไบต์เดียวกัน ปัญหาค่ากระโดดไปมาจึงไม่เกิด

| Offset | ชื่อ | ชนิด | เจ้าของ | ความหมาย |
|---|---|---|---|---|
| 0.0 | Heartbeat | Int | Partner | นับขึ้นทุกสแกน ใช้ดูว่าโปรแกรม Partner ยังวิ่งอยู่ |
| 2.0–2.3 | AreaRun · CIP · ReqFull · EStopOk | Bool | Partner | สถานะของโซนผลิตที่ลมต้องตอบสนอง |
| 4.0 | Demand | Int | Partner | ความต้องการลมของโซน (%) |
| 6.0 | Spare | Int | Partner | เผื่อไว้ เพิ่มสัญญาณได้โดยไม่ต้องเลื่อน Offset |
| 8.0 | Heartbeat | Int | S7-1200 | ให้ Partner รู้ว่าระบบลมยังคุยอยู่ |
| 10.0–10.3 | BlowerRun · FullMode · Fault · CommOk | Bool | S7-1200 | สถานะของระบบลมกลับไปให้ไลน์ผลิต |
| 12.0 | BlowerHz | Real | S7-1200 | ความถี่ Blower จริงจาก Inverter |
| 16.0 | Valves | Word | S7-1200 | บิต 0–10 = วาล์ว F1–F11 เปิดอยู่ |
| 18.0 | Alarms | Word | S7-1200 | Alarm ของระบบลม เช่น Blower run ≤ 30 Hz |

ฝั่ง S7-1200 ใช้ DB แบบ **Standard (ไม่ Optimized)** ที่มีโครงเหมือนกันทุกไบต์ ตัวละหนึ่ง DB ต่อ Partner
(`"IF_S7300"` และ `"IF_S7400"`) ข้างในมี Struct `FromPartner` ขนาด 8 ไบต์ และ `ToPartner` ขนาด 12 ไบต์
เวลาเปิดดูค่าใน TIA Portal กับเปิดดูใน S7-300 จะเห็นตัวเลขเดียวกันในตำแหน่งเดียวกัน ช่วยได้มากตอนไล่หาปัญหาหน้างาน

## ลองเล่นดู: ไบต์วิ่งยังไง

กล่องด้านล่างคือการจำลองการสื่อสารแบบที่เราทำไว้ S7-1200 วิ่ง **4 งานวนกัน** คือ GET S7-300 → PUT S7-300 → GET S7-400 → PUT S7-400
ดูช่องไบต์สีเขียวอมฟ้าตอน GET ไบต์ 0–7 จะถูกคัดลอกจาก Partner มาที่ S7-1200 ส่วนตอน PUT ไบต์ 8–19 สีม่วงจะถูกเขียนกลับไปที่ Partner

ลองกด **Request FULL** ที่ S7-400 แล้วดูว่า Blower กับวาล์ว F6–F11 เปลี่ยนตอนไหน จากนั้นลองใส่ Fault ทีละตัวครับ

<PutGetLink title="S7-1200 ↔ S7-300 / S7-400 · PUT/GET ทีละงาน" />

สิ่งที่อยากให้สังเกตจากการจำลองมี 3 อย่างครับ

1. **คำสั่งจากไลน์ผลิตไม่ได้ไปถึงทันที** ต้องรอให้วนมาถึงงาน GET ของ Partner ตัวนั้น ในเครื่องจริงหนึ่งรอบใช้เวลาระดับร้อยมิลลิวินาที
   เร็วพอสำหรับระบบลม แต่ **ไม่เหมาะกับสัญญาณ Safety หรือ Interlock ที่ต้องเร็ว** ซึ่งควรเดินสายตรง
2. **S7-300 STOP แต่ GET ยัง NDR** เพราะ CPU ในโหมด STOP ยังตอบ PUT/GET ได้ ค่าที่อ่านมาจึงเป็นค่าเก่าที่ค้างอยู่
   ถ้าเชื่อแค่ NDR ระบบลมจะทำงานตามสถานะที่ไม่จริง เราจึงใช้ **Heartbeat** ถ้าเลขไม่ขยับ 3 รอบติด ถือว่าขาดการติดต่อ
3. **พังแล้วต้องรู้ว่าพังแบบไหน** สายหลุดได้ `STATUS 1` ส่วนขนาดพื้นที่รับไม่เท่ากับที่ขอได้ `STATUS 4`
   เราแสดง STATUS ล่าสุดของทุกงานบนหน้า Network ของ HMI ช่างจะรู้ทันทีว่าต้องไปดูสายหรือไปดูโปรแกรม

## โค้ด SCL ที่ใช้วนงาน

นี่คือโครงที่เราเขียนขึ้นใหม่ให้เห็นหลักการ หัวใจคือ **REQ ของแต่ละงานเป็น TRUE เฉพาะตอนถึงคิวของมัน**
พอถึงคิวครั้งถัดไป REQ จะขึ้นใหม่ ได้ขอบขาขึ้นอัตโนมัติ ไม่ต้องใช้ Clock memory หรือ Timer มากระตุ้น

```pascal
// FB "VentLink" — S7-1200 is the client, one S7 connection per partner
// #step: 0 = GET S7-300, 1 = PUT S7-300, 2 = GET S7-400, 3 = PUT S7-400
#GET_S7300(REQ := #step = 0, ID := W#16#100,
           ADDR_1 := P#DB100.DBX0.0 BYTE 8,  RD_1 := "IF_S7300".FromPartner);
#PUT_S7300(REQ := #step = 1, ID := W#16#100,
           ADDR_1 := P#DB100.DBX8.0 BYTE 12, SD_1 := "IF_S7300".ToPartner);
#GET_S7400(REQ := #step = 2, ID := W#16#101,
           ADDR_1 := P#DB100.DBX0.0 BYTE 8,  RD_1 := "IF_S7400".FromPartner);
#PUT_S7400(REQ := #step = 3, ID := W#16#101,
           ADDR_1 := P#DB100.DBX8.0 BYTE 12, SD_1 := "IF_S7400".ToPartner);

// Move on when the job in this step has finished, good or bad
CASE #step OF
  0: #fin := #GET_S7300.NDR  OR #GET_S7300.ERROR; #st := #GET_S7300.STATUS;
  1: #fin := #PUT_S7300.DONE OR #PUT_S7300.ERROR; #st := #PUT_S7300.STATUS;
  2: #fin := #GET_S7400.NDR  OR #GET_S7400.ERROR; #st := #GET_S7400.STATUS;
  3: #fin := #PUT_S7400.DONE OR #PUT_S7400.ERROR; #st := #PUT_S7400.STATUS;
END_CASE;
IF #fin THEN
  #lastStatus[#step] := #st;          // shown on the HMI Network page
  #step := (#step + 1) MOD 4;
END_IF;

// NDR alone does not prove the partner's program is running: watch its heartbeat
IF #GET_S7300.NDR AND "IF_S7300".FromPartner.Heartbeat <> #hbOld300 THEN
  #hbOld300 := "IF_S7300".FromPartner.Heartbeat;
  #stale300 := 0;
ELSIF #GET_S7300.NDR OR #GET_S7300.ERROR THEN
  #stale300 := #stale300 + 1;
END_IF;
"IF_S7300".ToPartner.CommOk := #stale300 < 3;   // same block for the S7-400
```

## ตั้งค่าใน TIA Portal ทีละข้อ

1. **สร้าง S7 connection** ใน Devices & networks จาก S7-1200 ไปยัง Partner แบบ **Unspecified**
   เลือก Interface ฝั่งเราเป็น **CP 1243-1** เพราะเครือข่ายโรงงานต่ออยู่ที่ CP ไม่ใช่ Port ของ CPU
   ให้ฝั่ง S7-1200 เป็นคน **Active connection establishment** จะได้ ID (เช่น 16#100, 16#101) มาใช้ในโค้ด
2. **Rack / Slot ของ Partner ต้องถูก** S7-300 มักอยู่ Slot 2 ส่วน S7-400 ขึ้นกับความกว้างของ Power supply ต้องเปิด Hardware config ดูของจริง
   ตั้งผิดจะต่อไม่ติดและได้ `STATUS 1` ตลอด
3. **DB100 ต้องมีจริงและยาวพอ** ทั้งใน S7-300 และ S7-400 อย่างน้อย 20 ไบต์ ถ้า ADDR ชี้เกินขนาด DB งานจะ Error
4. **DB ฝั่ง S7-1200 เป็น Standard access** และขนาด `RD_1` / `SD_1` ต้องเท่ากับที่ `ADDR_1` ขอ
5. **การอนุญาต PUT/GET** ในหน้า Protection & Security ของ S7-1200 จำเป็นเฉพาะตอน S7-1200 เป็น **Server** ให้คนอื่นมาอ่านเขียน
   งานนี้ S7-1200 เป็น Client จึงไม่ต้องเปิด ส่วน S7-300 / S7-400 **ไม่มีสวิตช์นี้เลย** ใครเข้าถึงเครือข่ายได้ก็อ่านเขียนได้

<Callout type="safety" title="PUT/GET ไม่มีรหัสผ่าน">
PUT/GET เป็นโปรโตคอลที่ไม่มีการยืนยันตัวตน เครื่องไหนอยู่ในเครือข่ายเดียวกันและรู้ Address ก็เขียนค่าลง PLC ได้
นี่คือเหตุผลที่เราแยกเครือข่ายเครื่องออกจากเครือข่ายโรงงานด้วย CP 1243-1 และให้ข้อมูลข้ามได้เฉพาะ DB ที่ตกลงกันไว้
เรื่องนี้เล่าละเอียดไว้ใน [บทความ OT Security สำหรับโรงงาน](/blog/ot-security-factory/) ครับ
</Callout>

## หน้าจอ HMI ที่ออกแบบเอง

![ภาพวาดหน้าจอ HMI TP700 แบบใหม่ ด้านบนเป็นแถบสถานะ แสดงโหมด FULL, Blower 50.0 Hz และไฟสถานะการสื่อสารกับ S7-300 และ S7-400 ตรงกลางเป็นวาล์วลม F1 ถึง F11 แต่ละตัวมีแถบ % เปิด 100, 100, 66, 45, 58, 54, 54, 55, 60, 60 และ 67 ด้านข้างเป็นการ์ด Blower และ Time off 30 กับ 60 วินาที](./hmi.webp)

<small>ภาพวาดหน้าจอแบบปรับให้ทันสมัยขึ้น จากหน้าจอจริงในวิดีโอทดสอบ ค่าตัวเลขเป็นค่าจริงจากหน้า Manual และ Parameter</small>

หน้าจอทั้งหมดเราออกแบบเองบน TP700 Comfort ทุกหน้ามีแถบหัวเดียวกัน คือวันเวลา ชั่วโมงการทำงานของระบบ ไฟสถานะ G / Y / R และปุ่มล็อกอิน
และแถบเมนูด้านข้างที่กดไปได้ทุกหน้าในหนึ่งแตะ

| หน้าจอ | สิ่งที่ทำได้ |
|---|---|
| Home | หน้าแรกและเมนูหลัก |
| Overview | ผังห้องจริงของโรงงาน แสดงแนวท่อลม ตำแหน่ง Blower และวาล์ว F1–F11 พร้อมปุ่มไปหน้า P&ID |
| Manual | สั่ง Blower ON/OFF ตั้ง % และดูความถี่ (100 % = 50 Hz) เปิดปิดวาล์วทีละตัว ตั้ง **Time off Blower 30 s** และ **Time off Valve 60 s** และปุ่ม Stop All |
| Auto | สองโหมด **NORMAL** กับ **FULL** แต่ละโหมดตั้งความเร็ว Blower และ % เปิดวาล์วแยกกัน เลือกวาล์วที่ใช้ในโหมด Normal ได้ทีละตัว |
| Alarm | Alarm ปัจจุบันและประวัติ เช่น **Blower run ≤ 30 Hz** และ **Emergency Stop** |
| Parameter | ตารางเดียวรวมค่า % ของวาล์วทุกตัว ความถี่ Blower และ Time off |
| Network | Diagnostic ของ S7-300, S7-400, CP 1243-1, S7-1200, Switch และ HMI ในหน้าเดียว |

ทำไม % เปิดของวาล์วแต่ละตัวไม่เท่ากัน (F1 100 %, F4 45 %, F11 67 %)? เพราะท่อแต่ละเส้นยาวและโค้งไม่เท่ากัน
จุดที่อยู่ใกล้ Blower ถ้าเปิดเต็มจะแย่งลมไปหมด ตอน Commissioning เราจึง **วัดความเร็วลมที่หน้างาน** แล้วปรับ % ของวาล์วทีละตัวจนลมออกสมดุล
ค่าที่ได้เก็บไว้ในหน้า Parameter ให้ปรับต่อได้โดยไม่ต้องแก้โปรแกรม

Blower หยุดก่อนวาล์ว: เมื่อไม่มีโซนไหนต้องการลม Blower จะหยุดหลัง 30 วินาที และวาล์วจะปิดหลัง 60 วินาที
ลำดับนี้ทำให้ Blower **ไม่ต้องอัดลมเข้าท่อที่วาล์วปิดหมดแล้ว**

## ถ้าทำวันนี้ เราจะทำให้ทันสมัยขึ้นอีก 5 เรื่อง

1. **เก็บโปรเจคไว้ใน Version control** บทเรียนตรงที่สุดของงานนี้คือไฟล์หาย ทุกวันนี้เราเก็บ TIA Portal Project, Archive (.zap)
   และไฟล์ Export ของ Block ไว้ใน Git พร้อม Tag ตามวันที่ลงเครื่องจริง
2. **แผนย้ายจาก S7-300 / S7-400** S7-300 เข้าช่วงเลิกผลิตแล้ว เมื่อไลน์ผลิตย้ายไป S7-1500 ควรเปลี่ยนจาก PUT/GET
   เป็น **PROFINET I-Device** หรือ **OPC UA** ที่มีสิทธิ์การเข้าถึงชัดเจน
3. **Interface เป็น UDT ไฟล์เดียว** ใช้โครงเดียวกันทั้งฝั่ง Client และ Server พร้อมเลขเวอร์ชันในไบต์แรก ถ้าใครแก้โครงข้างเดียวจะรู้ทันที
4. **HMI แบบ High-performance** พื้นเทา สีใช้เฉพาะตอนผิดปกติ และแสดง STATUS ของทุกงาน PUT/GET แบบในการจำลองข้างบน
5. **ส่งข้อมูลลมขึ้น Unified Namespace** ชั่วโมงทำงานของ Blower, Alarm และ % วาล์ว ส่งขึ้น [UNS](/blog/unified-namespace-mqtt-ignition-grafana/)
   ให้ทีมซ่อมบำรุงเห็นแนวโน้มก่อน Blower เสีย

## 5 บทเรียนเรื่อง PUT/GET ที่ใช้ได้ทุกงาน

1. **ฝั่งไหนเป็น Client ฝั่งนั้นถือคิว** วนงานทีละงาน รู้ว่ากำลังทำอะไรอยู่เสมอ
2. **ไบต์ทุกตัวมีเจ้าของคนเดียว** แบ่งโซนอ่านกับโซนเขียนให้ชัด
3. **Offset ต้องตรงกันทั้งสองฝั่ง** ใช้ DB แบบ Standard และเผื่อ Spare ไว้ตั้งแต่วันแรก
4. **NDR ไม่ได้แปลว่าอีกฝั่งยังมีชีวิต** ต้องมี Heartbeat
5. **PUT/GET ไม่ใช่สาย Safety** ใช้กับข้อมูลสถานะและคำสั่งที่รอได้ระดับร้อยมิลลิวินาที
